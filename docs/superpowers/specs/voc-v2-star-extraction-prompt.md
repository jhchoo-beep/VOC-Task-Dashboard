# VOC V2 별 추출 지침

- 용도: 리뷰에서 **별**(이용객 목소리 1개)을 뽑는 LLM 지침. 2026-10-13 백필(신설·동대문 2026-06~10, 674건 → 별 2,105개)에 쓴 규칙을 고정한 것이다. 앞으로 월요일 루틴이 그 주 새 리뷰에 같은 지침을 쓸 수 있게 입력, 출력, 검증을 정해 둔다.
- 🔴 이 문서는 루틴을 만들거나 바꾸지 않는다. 루틴 연결은 V2 가동 승인 뒤의 별도 작업이다(6절).
- 정본: 설계서 `2026-10-12-voc-v2-constellation-design.md` 4절, 검증 코드 `scripts/v2/build-stars.ts`. 별자리 묶음(같은 현상 → 씨앗·별자리)은 추출이 아니라 `lib/v2/constellationRules.ts`가 한다.
- 첫 가동 원천은 OTA 리뷰뿐이다. 채널톡, LIVE 이용객 경험도 같은 별 형식을 쓴다(7절).

## 1. 역할(LLM에 그대로 준다)

> 너는 숙소 리뷰에서 이용객의 목소리를 하나씩 떼어 기록한다. 리뷰가 말한 사실만 옮긴다. 원인을 추정하지 않고, 무엇을 고쳐야 하는지 판단하지 않는다. 같은 현상에는 현상 사전에 있는 이름을 그대로 쓴다. 출력은 아래 형식의 JSON 하나뿐이다.

## 2. 입력

배치 하나 = 원문 있는 리뷰 최대 40건, JSON 배열.

```json
[{"id": "리뷰 uuid", "branch": "신설", "channel": "Agoda", "date": "2026-06-01", "rating": 4, "scale": 10,
  "ko": "reviews.content_ko(한국어 리뷰는 원문 그대로, 외국어 리뷰는 번역)", "orig": "reviews.content"}]
```

- 리뷰어 이름, 국적, 객실 번호 칸은 넣지 않는다.
- 함께 주는 것: **현상 사전** = 지금까지 쓴 현상 이름 목록(지점, 극성, 은하, 현상, 받는 쪽). 운영에서는 `select distinct branch, polarity, galaxy, phenomenon, owner from voc_stars`로 만든다. 백필은 `data/phenomena.json`.
- 중복 리뷰(같은 지점·채널에서 공백 뺀 본문 앞 60자가 같은 리뷰, 원문과 번역본이 두 행으로 들어간 리뷰)는 별을 내지 않는다. 입력 전에 빼는 것이 가장 단순하다. 입력에 남기면 `reviews` 목록에는 넣고 별은 내지 않는다(검증이 막는다).

## 3. 출력

```json
{
  "batch": "NN",
  "format": "[review_id8, polarity p|n, galaxy code, phenomenon, quote(content_ko 발췌), owner CM|CR|FM|X, relation_signal E|R|C|P|null]",
  "reviews": ["입력 리뷰 id 앞 8자 전부 — 별이 없는 리뷰도 넣는다"],
  "stars": [
    ["1a2b3c4d", "n", "시", "객실 TV 없음", "TV가 없어요", "X", null],
    ["1a2b3c4d", "p", "청", "객실 깨끗함", "방은 깨끗했어요", "CM", null]
  ]
}
```
(별 두 줄은 형식 예시다.)

### 코드 표

| 칸 | 코드 |
|---|---|
| 극성 | `p` 칭찬, `n` 불편 |
| 은하 | `청` 청결, `소` 소음, `시` 시설, `응` 응대/환대/커뮤니티, `체` 체크인/체크아웃, `위` 위치/접근성, `어` 어메니티, `가` 가격, `기` 기타 |
| 받는 쪽 | `CM`, `CR`, `FM`, `X`(운영 밖) |
| 관계 신호 | `E` 감정 고조, `R` 재문의, `C` 보상 요구, `P` 평판 리스크, 없으면 `null` |

## 4. 규칙

### 4.1 무엇이 별인가
- 별 = 이용객이 겪은 구체적인 대상이나 경험 하나에 대한 목소리. 리뷰 한 건에서 여러 개가 나온다(백필 평균 3.5개).
- 한 리뷰에서 같은 현상·같은 극성은 별 하나다. 같은 말을 두 번 했으면 더 잘 드러나는 구절 하나를 발췌로 쓴다. 현상 사전에서 한 이름으로 합쳐진 표현도 같은 현상이다(예: 「호텔식 서비스 없음」은 「셀프 운영 번거로움」에 합쳐졌다 — 한 리뷰에 둘 다 있으면 「셀프 운영 번거로움」 별 하나).
- 한 문장에 칭찬과 불편이 같이 있으면 각각 별로 만든다(예: 「방은 좁지만 깨끗해요」 → 불편 「객실 좁음」 + 칭찬 「객실 깨끗함」).
- 별로 만들지 않는 것: 구체적인 대상이 없는 총평, 감탄, 추천, 재방문 의사, 점수 언급(예: 「좋았어요」, 「또 올게요」, 「다시는 안 올 것 같아요」). 이런 리뷰는 `reviews`에만 넣고 별은 0개다.

### 4.2 현상 이름
- 「공간 + 현상」으로 쓴다. 공간 = 객실, 욕실, 도미토리, 공용 주방, 세탁실, 복도, 엘리베이터, 루프탑, 로비 등. 현상 = 이용객이 보고 겪은 것(예: 욕실 샤워 후 바닥 젖음, 객실 에어컨 자동 꺼짐, 셀프 체크인 편리).
- 🔴 원인, 담당, 처방을 이름에 넣지 않는다.
  - ✗ 「HK 정비 품질 불량」(원인·담당) → ✓ 「객실 먼지·오염」, 「욕실 머리카락」
  - ✗ 「셀프 운영 사전 고지 부족」(원인 가설) → ✓ 「셀프 운영 번거로움」
- **현상 사전에 같은 현상이 있으면 그 이름을 글자 그대로 쓴다.** 이름이 다르면 같은 현상이 묶이지 않아 별자리가 생기지 않는다. 사전에 없을 때만 새 이름을 만든다.
- 같은 이름은 극성마다 은하와 받는 쪽이 하나여야 한다(사전의 값을 따른다).
- 괄호, 객실 번호, 사람 이름, 「고객」을 쓰지 않는다(「이용객」).
- 칭찬은 칭찬 이름으로 쓴다(예: 객실 깨끗함, 직원 친절·환대, 위치·교통 편리).

### 4.3 은하
- 청결: 객실·욕실·침구·공용 공간의 깨끗함과 오염, 머리카락, 먼지, 객실 냄새, 벌레, 투숙 중 청소
- 소음: 옆방·복도·도로·설비·도미토리 소음, 조용함
- 시설: 객실과 욕실의 설비·구조·고장·노후, 냉난방, 와이파이, 공용 시설(주방, 세탁실, 루프탑, 헬스장), 출입 설비
- 응대/환대/커뮤니티: 직원 응대와 친절, 문의 응답, 요청 반영, 셀프 운영 체감, 커뮤니티
- 체크인/체크아웃: 셀프 체크인, QR 출입, 체크인 시간, 짐 보관, 이용 안내 표시
- 위치/접근성: 교통, 주변 편의시설, 동네 치안, 공항 오가기
- 어메니티: 객실 비품과 어메니티의 유무·품질, 수건, 슬리퍼, 세제, 어댑터
- 가격: 가격 수준, 가성비, 유료 항목
- 기타: 숙소 전반의 안전감, 카페·조식, 실내 향기, 다른 이용객 매너, 혼잡
- V1 「직원서비스」는 「응대/환대/커뮤니티」로 쓴다. V1 「보안」은 은하가 아니다: 출입 설비 = 시설, QR·체크인 출입 = 체크인/체크아웃, 동네 치안 = 위치/접근성, 숙소 전반 안전감 = 기타.

### 4.4 받는 쪽
- `CM`: 응대, 입퇴실, 정비·위생, 어메니티, 환대, 운영 안내
- `FM`: 시설·설비(고장, 노후, 배수, 냉난방, 소음 차단 등)
- `CR`: 관계의 균열 자체가 현상인 경우
- `X`(운영 밖): 위치, 가격 수준, 건물 구조(TV 없음, 객실 크기, 욕실 크기 등) — 운영이 바꿀 수 없는 것
- 예: 객실 냄새 = CM, 욕실 하수구 냄새 = FM, 객실 좁음 = X, 짐 보관 유료 = CM, 숙박 가격 비쌈 = X

### 4.5 발췌
- 입력의 `ko`에 **그대로 있는** 구절을 복사한다. 고치거나 요약하거나 다른 말로 바꾸지 않는다. 공백 차이만 허용한다. `orig`에서 뽑지 않는다.
- 그 목소리를 담은 가장 짧은 구절(백필 3~83자, 평균 22자).
- 한 구절이 두 현상을 함께 말하면 같은 발췌를 두 별에 써도 된다.

### 4.6 관계 신호
- 리뷰당 최대 1개, 가장 해당하는 **불편** 별에만 붙인다. 칭찬 별에는 붙이지 않는다.
- `P` 평판 리스크: 다른 사람에게 경고하거나 극단적으로 평가함(「여기 오지 마세요」 등)
- `E` 감정 고조: 무례, 최악 등 강한 감정
- `R` 재문의: 여러 번 말해야 했음
- `C` 보상 요구: 환불·보상을 요구함
- 백필 23개(P 16, E 5, R 2, C 0).

## 5. 검증(`scripts/v2/build-stars.ts`, 하나라도 어긋나면 그 배치를 다시 뽑는다)

- `reviews`가 입력 리뷰와 정확히 같은가(빠짐, 남는 것 없음)
- 별의 리뷰가 그 배치 안에 있는가, 중복 리뷰에서 별이 나오지 않았는가
- 극성, 은하, 받는 쪽, 관계 신호 코드가 표 안에 있는가, 현상 이름에 괄호가 없는가
- 발췌가 `content_ko` 안에 그대로 있는가. 통과하면 원문 위치(코드포인트 시작, 길이)를 남기고, 그 위치로 다시 잘라 낸 조각이 발췌와 같은지 확인한다
- 같은 리뷰에서 같은 현상·같은 극성이 두 번 나오지 않았는가
- 같은 현상 이름이 극성마다 은하·받는 쪽 하나인가

## 6. 루틴에서 쓸 때(아직 만들지 않음)

V2 가동 승인 뒤 월요일 루틴에 붙일 때의 순서다. 지금 루틴은 바꾸지 않았다.

1. 그 주에 새로 들어온 reviews 중 원문 있는 리뷰를 고르고, `resolve-dates.ts`와 같은 규칙(`lib/otaDetail.ts`)으로 날짜를 정한다. 중복 리뷰를 뺀다.
2. 40건씩 나눠 이 지침 + 현상 사전 + 입력으로 LLM을 부른다.
3. 5절 검증을 통과한 배치만 쓴다.
4. 새 별에 `voc_stars`의 마지막 번호 다음부터 `S-NNNNN`을 매긴다. 기존 ID는 바꾸지 않는다. 발췌는 옮겨 적지 않고 서버에서 `substr(content_ko, 시작+1, 길이)`로 넣는다. upsert라 같은 배치를 다시 넣어도 결과가 같다(고유 키 = 원천, 원천 ID, 극성, 현상 — 한 리뷰·한 극성·한 현상은 별 하나).
5. 별자리 재판정(`constellationRules.ts`) → 상태·이력 → 지표 → 주간 리포트 입력 선택(설계서 8절) 순서로 이어진다. 현상 이름을 새로 합치면, 합친 뒤 같은 리뷰·같은 극성·같은 현상 별은 하나만 남긴다(설계서 5.1절).

## 7. 다른 원천(채널톡, LIVE)

- 같은 별 형식을 쓴다. `source` = `channel_talk` 또는 `live`, `source_ref` = 상담 ID 또는 해당 원천 ID, `review_id` = null.
- 입력의 `ko`는 상담·기록 본문으로 바꾸고, 발췌 규칙(본문에 그대로 있는 구절)은 같다.
- 카테고리 맞추기와 연결은 채널톡·LIVE를 붙일 때 정한다(기획 결정 3, 6).
