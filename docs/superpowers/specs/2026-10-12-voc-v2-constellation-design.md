## 1. 구조 한 줄

이용객 목소리 1개 = **별**. 같은 지점·같은 현상의 별이 반복되면 **씨앗**(2개) → **별자리**(3개 이상, 서로 다른 2주 이상, 최근 90일). 수행과제 완료 뒤 3개월 동안 새 별이 0건이면 **성운**. 카테고리 9개가 **은하**, 두 지점의 은하가 모인 것이 **우주**, 최종 지표가 **북극성**(불편 없이 끝난 체류 비율).

- 단발 별은 주간 리포트에서 그 주에 처리하고 끝낸다(8절).
- 반복은 별자리로 묶어 수행과제 후보로 둔다. 묶음과 이름은 LLM이 자동 확정하고, 수행과제로 등록할지는 FO가 정한다.

## 2. 원칙

- 앱과 LLM은 원인 문구와 조치 판단(무엇을 고쳐라, 왜 생겼다)을 만들지 않는다. 별자리 이름 = 「공간 + 현상」, 요약 = 이용객이 말한 사실 한 문장. 처방 자리에는 시스템 상태(연결된 수행과제 제목과 상태, 「수행과제 등록 여부 FO 결정 대기」)만 둔다.
- 기준값(씨앗 2, 별자리 3, 서로 다른 2주, 90일)은 결과를 보고 바꾸지 않는다. 바꾸면 다음 분기부터 적용한다.
- V1 표(reviews, raw_reviews, review_triage, tasks, weekly_tasks, task_logs, ota_*)는 읽기만 한다. 새 표는 `voc_` 접두어, RLS를 켜고 SELECT 정책만 둔다.
- 리뷰 전문은 새 표에 복사하지 않는다(`review_id`로 reviews 참조). 리뷰어 이름은 어디에도 넣지 않는다. 별자리 이름에 객실 번호를 넣지 않는다.
- 표기는 「고객」 대신 「이용객」.

## 3. 표 구조

### 3.1 `voc_stars` — 별

| 칸 | 내용 |
|---|---|
| `id` | `S-NNNNN`. 백필은 지점 → 날짜 → 리뷰 → 발췌 위치 순으로 매김. 루틴은 다음 번호부터 이어서 매기고 기존 ID는 바꾸지 않는다 |
| `source`, `source_ref` | 원천 3종 공통 형식. `ota_review`(= reviews.id), `channel_talk`(상담 ID), `live`(해당 원천 ID). 첫 가동은 OTA 리뷰만 |
| `review_id` | `source='ota_review'`일 때 reviews.id. 외래키 없음 |
| `branch`, `channel` | 채널은 `ota_properties.ota_name` 표기(Agoda, Booking, Trip.com, Expedia, Airbnb, NOL, 여기어때) |
| `star_date`, `date_source` | 별 날짜와 출처(`raw`, `collected`, `month`) — 4.1절 |
| `iso_week` | `YYYY-Www`(ISO 주, 월~일). 별자리 「서로 다른 2주」 판정 기준 |
| `week_label` | 주간 리포트 버킷. `lib/otaDetail.ts` `weekLabelOf` = 화~월 구간의 끝 월요일 |
| `polarity`, `galaxy`, `phenomenon`, `owner` | 극성(neg, pos), 은하 9개, 현상 이름, 받는 쪽(CM, CR, FM, 운영 밖) |
| `quote` | 리뷰 번역본(`reviews.content_ko`)에서 이 목소리에 해당하는 발췌. 적재 때 서버가 `substr`로 잘라 넣는다 |
| `relation_signal` | 감정 고조, 재문의, 보상 요구, 평판 리스크 중 하나 또는 null(CR 신호) |
| `constellation_id` | 별자리·씨앗 ID. 단발 별은 null. `voc_constellations.id` 외래키(on delete set null) |
| `extracted_by` | `llm-backfill-2026-10-13` 등 |

### 3.2 `voc_constellations` — 별자리와 씨앗

| 칸 | 내용 |
|---|---|
| `id` | `C-<지점>-NNN`. 지점별로 별자리(생성일 순) 다음 씨앗(첫 별 순), 같으면 이름 순. 운영에서는 생성 때 부여하고 바꾸지 않는다 |
| `branch`, `polarity`, `galaxy`, `name`, `owner` | 이름은 현상 이름 그대로(「공간 + 현상」) |
| `status` | 부정: 씨앗, 열림, 수행과제 진행, 관찰, 성운, 재발 / 긍정: 씨앗, 유지, 흐려짐. 극성과 상태 조합은 CHECK 제약으로 막는다 |
| `formed_at` | 별자리 조건을 처음 채운 날(씨앗은 null) |
| `first_date`, `last_date`, `star_count`, `distinct_weeks`, `recent_4w` | 구성 별 기준. `recent_4w` = 기준일 포함 28일 별 수 |
| `monthly`, `channels` | 월별·채널별 별 수(jsonb) |
| `task_id` | 연결된 수행과제(tasks.id). 외래키 없음 |
| `observation_start`, `nebula_at`, `relapse_count` | 관찰 시작일(연결 과제 완료일), 성운 전환일, 재발 횟수 |
| `summary` | 이용객이 말한 사실 요약 한 문장. 원인·처방 없음 |
| `sort_order` | 지점·극성 안 순서(5.5절) |
| `as_of` | 이 행 값의 기준일 |

### 3.3 `voc_constellation_events` — 별자리 이력

`id` = `<별자리 ID>#NN`(적재를 다시 해도 같은 행). `event_type` = seed, formed, merge, split, rename, task_linked, observing, relapse, nebula, fading, kept, status_change. `actor` = `llm-backfill-2026-10-13`, 앞으로 `routine`, `fo:<이름>`. 별자리 외래키 on delete cascade.

### 3.4 `voc_metrics_monthly` — 월 지표

키 `(branch, month, channel)`. 백필 80행 = 지점·월 「전체」 10행(별 날짜 기준 은하별 부정·긍정 별 수) + 지점·채널·월 70행(북극성, 목소리 비율, 산출 근거 `inputs`). 채널 행의 달은 주 라벨이 속한 달이다. 채널 행은 `is_estimate = true`.

### 3.5 키와 보안

- V1 표에 외래키를 걸지 않는다. 걸면 V1의 리뷰·과제 삭제가 막히거나(RESTRICT) 별이 조용히 지워진다(CASCADE). 참조 무결성은 적재 검증(`90-verify.sql`의 `stars_without_review`)으로 본다.
- `voc_stars` 고유 키 `voc_stars_one_voice` = `(source, source_ref, polarity, phenomenon)`. 한 원본·한 극성·한 현상 = 별 하나(별 = 리뷰 속 목소리 1개). 백필 적재 중 A4 현상 합침 뒤 같은 리뷰에서 같은 현상 별이 2개가 된 3쌍이 이 키에 걸렸다. 한때 키에 발췌를 더했으나(`voc_v2_stars_unique_quote`), 규칙을 느슨하게 두지 않고 데이터를 고치기로 해(5.1절, 11절) 원래 키로 되돌렸다(`voc_v2_stars_unique_voice_restore`).
- RLS: 4개 표 모두 켬. anon, authenticated에 SELECT 정책만 있고 쓰기 정책은 없다. 쓰기는 서비스 역할(마이그레이션, 적재, 앞으로의 루틴)만 한다. 앱은 anon 키로 서버에서 읽는다.
- 확인(2026-10-13, PostgREST, anon 키): 4개 표 GET 200, `voc_constellations` POST 401(42501 RLS 위반), PATCH·DELETE는 오류 없이 영향 0행. 시험 뒤 체크섬으로 변경 없음 확인.
- 인덱스: 별자리(지점·극성·상태), 별자리 과제, 별(별자리, 지점·날짜, 리뷰, 주 라벨), 이력(별자리·날짜).

## 4. 별 추출

### 4.1 원천과 날짜

- 원천: `reviews`의 신설·동대문, `review_month` 2026-06~10. 723건(신설 364, 동대문 359), 원문 있는 리뷰 674건(339, 335).
- 날짜는 `lib/otaDetail.ts`의 `pairReviewsWithRaw`, `reviewKey`, `resolveReviewDate`를 그대로 쓴다(`scripts/v2/resolve-dates.ts`). 새 규칙을 만들지 않는다.
  - `raw`: `raw_reviews.raw_date`의 일자
  - `collected`: 아고다처럼 주 단위 채널인데 일자가 없으면 raw 수집일
  - `month`: 짝을 못 찾으면 `review_month` 15일(기준일을 넘으면 기준일)
  - 백필: raw 523, collected 128, month 72
- 주는 두 가지를 함께 저장한다. 별자리 「서로 다른 2주」는 ISO 주(`iso_week`), 주간 리포트 연결은 화~월 버킷(`week_label`). 둘은 하루 어긋나므로 섞어 쓰지 않는다.

### 4.2 추출 단위와 값

- 별 = 이용객 목소리 1개. 리뷰 한 건에서 여러 개가 나온다(백필 평균 3.5개, 최대 13개).
- 한 리뷰·한 현상·한 극성에서는 별 하나만 낸다. 추출 때는 `build-stars.ts`가 검사하고, A4 현상 합침 뒤에는 `build-universe.ts`가 하나만 남긴다(5.1절).
- 구체적인 대상이 없는 총평, 추천, 재방문 의사는 별로 만들지 않는다(백필에서 원문 있는 리뷰 52건이 별 0개).
- 은하 9개: 청결, 소음, 시설, 응대/환대/커뮤니티, 체크인/체크아웃, 위치/접근성, 어메니티, 가격, 기타. V1 표의 「직원서비스」 값은 바꾸지 않고 새 표와 화면에서만 「응대/환대/커뮤니티」를 쓴다. V1 「보안」 태그는 은하가 아니므로 출입 설비 = 시설, QR·체크인 출입 = 체크인/체크아웃, 동네 치안 = 위치/접근성, 숙소 전반 안전감 = 기타.
- 받는 쪽(만성 문제 실행 주체, CM 미션·역할경계 위키 기준): CM = 응대, 입퇴실, 정비·위생, 어메니티, 환대, 운영 안내 / FM = 시설·설비 / CR = 관계 균열이 현상 자체인 경우 / 운영 밖 = 위치, 가격 수준, 건물 구조(TV 없음, 객실 크기 등). 백필: CM 878, 운영 밖 823, FM 404, CR 0.
- 관계 신호: 리뷰당 1개, 가장 해당하는 부정 별에만 붙인다. 평판 리스크 = 다른 사람에게 경고하거나 극단 평가, 감정 고조 = 무례·최악 등 강한 감정, 재문의 = 여러 번 말해야 했음, 보상 요구. 백필 23개(평판 리스크 16, 감정 고조 5, 재문의 2). CR이 받는 쪽인 별이 0이라 관계 문제는 이 신호로만 보인다.
- 발췌: `content_ko`에 그대로 있는 조각(공백만 정규화). 추출 때 원문 위치(코드포인트 시작, 길이)를 함께 남기고, 운영 표 적재는 그 위치로 서버에서 `substr(content_ko, 시작+1, 길이)`를 잘라 넣는다. 발췌를 옮겨 적지 않으므로 화면과 DB 발췌가 글자 하나까지 같다.
- 중복 리뷰: 같은 지점·채널에서 본문 키(공백 뺀 앞 60자, 20자 이상)가 같으면 같은 목소리로 보고 가장 이른 1건에서만 별을 낸다. 원문과 번역본이 두 행으로 들어간 것은 사람이 원문을 대조한 것만 수동으로 지정한다. 백필 16건(자동 9, 수동 7). 별을 두 번 만들면 다른 주·달의 반복으로 보여 별자리가 부풀려진다.
- 지침 전문(입력, 출력 형식, 코드 표, 금지 사항)은 `voc-v2-star-extraction-prompt.md`.

### 4.3 추출 검증 — `scripts/v2/build-stars.ts`

하나라도 어긋나면 비정상 종료한다.
- 배치가 입력 리뷰를 빠짐없이 다뤘는가(입력 목록 = 출력 `reviews`)
- 별의 리뷰가 그 배치에 있는가, 중복 리뷰에서 별이 나오지 않았는가
- 은하, 받는 쪽, 관계 신호 코드가 목록 안인가, 현상 이름에 괄호가 없는가
- 발췌가 `content_ko` 안에 그대로 있는가, 위치로 다시 잘라 낸 조각이 발췌와 같은가(이모지 앞 위치 밀림을 여기서 막는다)
- 같은 리뷰에서 같은 현상·같은 극성이 두 번 나오지 않았는가
- 같은 현상 이름은 극성별로 은하와 받는 쪽이 하나인가

## 5. 별자리 판정 — `lib/v2/constellationRules.ts`

순수 함수, vitest 26건. 현상 판정(무엇이 같은 현상인가)은 LLM 몫이고, 이 파일은 같은 현상으로 묶인 별 목록에 숫자 규칙만 적용한다.

### 5.1 묶는 키와 현상 이름 합침
- 묶는 키 = 지점 + 극성 + 현상 이름. 같은 지점의 같은 현상이 기준이다. 카테고리(은하)와 받는 쪽은 별자리 속성이다.
- A4 합침(`data/a4-curation.json`): 같은 현상인데 이름이 달랐던 것을 합친다. 백필 합침 3건(호텔식 서비스 없음 → 셀프 운영 번거로움, 불만 제기 후 조치 지연·객실 고장 조치 미흡 → 문제 제기 후 조치 미흡·지연), 분리 유지 7건, 추출 중 이름 정리 32건. 합침은 별자리 이력에 `merge`로 남는다.
- 합친 뒤 같은 리뷰에서 같은 극성·같은 현상 별이 둘 이상이면 하나만 남긴다(2026-10-13 결정, 정의 「별 = 리뷰 속 목소리 1개」). 남기는 별 = 합침 전 이름이 별자리 이름과 같은 별이고, 빠지는 별의 관계 신호는 남기는 별로 옮긴다. 별 ID를 매긴 뒤에 빼므로 나머지 별 ID는 바뀌지 않는다(운영 표 upsert 키 유지). 기록은 `universe.json` `meta.voice_dedup`. 백필: S-01837·S-02014·S-02025를 빼고 S-01838·S-02015·S-02026을 남김(모두 C-신설-033, 평판 리스크는 S-01838·S-02015로 옮김). 코드는 앱 브랜치 `feat/voc-v2-app` 커밋 `53c0965`의 `scripts/v2/build-universe.ts`.

### 5.2 별자리 조건과 생성
- 별자리 = 같은 현상의 별 3개 이상이 서로 다른 ISO 주 2개 이상에 걸침, 같은 90일 창 안. 90일 = 기준일 포함 90일(기준일-89일 ~ 기준일).
- 「서로 다른 2주」는 한 주에 몰린 사건을 단발로 남기기 위한 조건이다.
- 생성은 재생으로 판정한다. 별 날짜를 하나씩 기준일로 보고 그날의 90일 창을 본다(같은 날 별은 함께 넣는다). 처음 조건을 채운 날 = `formed_at`.
- 구성원 = 생성 때 창의 첫날 이후 별 전부. 생성 뒤에는 90일이 지나도 같은 별자리(고정 ID)이고 이후 별도 붙는다. 생성 창보다 앞선 별은 단발로 남는다(그때 이미 주간 리포트에서 처리된 별).

### 5.3 씨앗과 단발
- 씨앗 = 별자리가 생긴 적 없고, 기준일 90일 창 안에 같은 현상 별이 2개 이상(같은 주에 3개가 몰린 경우 포함). 관찰만 한다.
- 단발 = 나머지(`constellation_id` null).

### 5.4 이름과 요약
- 이름 = 「공간 + 현상」(예: 욕실 샤워 후 바닥 젖음). 원인 없음, 괄호 없음.
- 요약 = 이용객이 말한 사실 한 문장(`data/summaries.json` 159건). 원인 추정과 처방 금지.

### 5.5 순서
지점·극성 안에서 최근 4주(기준일 포함 28일) 별 수 내림차순 → 마지막 별 날짜 최근 순 → 이름. 불편 크기로 가중하지 않는다.

## 8. 주간 리포트 연결(확정 결정 4)

### 8.1 규칙(재헌 2026-10-12)
- 주간 리포트 입력 = 점수와 상관없이 그 주 부정 별 중 단발 별만.
- 🔴 별자리에 붙은 부정 별은 주간 리포트에 나오면 안 된다. 한 리뷰에 단발 별과 별자리 별이 섞이면 단발 별만 나온다.
- 씨앗 단계 별은 나온다(별자리가 되기 전 첫 두 건도 그 주에 해결되게).
- 긍정 별자리는 원문 없이 「긍정 별자리마다 이번 주 붙은 긍정 리뷰 수」만 보여 준다.

### 8.2 표로 읽는 법
주 = `voc_stars.week_label`(V1 주간 리포트와 같은 화~월 버킷).

```sql
-- 부정 항목: 그 주 단발 별 + 씨앗 별
select s.*
from voc_stars s
left join voc_constellations c on c.id = s.constellation_id
where s.polarity = 'neg' and s.week_label = :week
  and (s.constellation_id is null or c.status = '씨앗');

-- 긍정 지표: 긍정 별자리마다 이번 주 붙은 긍정 리뷰 수
select c.id, c.name, count(distinct s.review_id) as reviews_this_week
from voc_constellations c
join voc_stars s on s.constellation_id = c.id
where c.polarity = 'pos' and c.status <> '씨앗' and s.week_label = :week
group by c.id, c.name;
```

- 별자리 상태는 기준일 시점 값이다. 주간 리포트를 만들 때는 그 주 별 추출 → 별자리 재판정 → 위 선택 순서로 해야 한다. 그 주에 별자리 조건을 채운 별은 별자리 별이 되어 리포트에서 빠진다.

### 8.3 구현 상태
- 바꾸지 않았다. V1 주간 리포트(9.0 미달 리뷰 전수와 판단 층)는 그대로 운영한다. 전환은 V2 가동 때(재헌 승인 뒤)이며, 월요일 루틴에서 별 추출이 돌아야 가능하다. 월요일 루틴 변경은 이번 작업 범위 밖이다.

## 10. 알려진 한계

- **체크아웃 원천**: 운영 DB `ota_channel_checkouts`는 신설 Agoda 수기 입력뿐이다. 북극성과 목소리 비율은 Wings 실 퇴실로 다시 뽑았고, 주간 결과를 property 단위로 옮기는 변환은 코드로 남아 있지 않다(4단계). 루틴으로 돌리려면 Wings 조회와 변환을 스크립트로 묶어야 한다.
- **추정치**: 북극성은 리뷰 1건 = 체류 1건 추정이다. 원문 커버리지가 채널마다 다르다(아고다 원문 31~34%). 여기어때 두 채널은 원문이 0건이라 북극성에서 빠진다. 동대문 Booking은 18주 동안 리뷰 수 증가가 0이다(수집 문제 의심, 기존 미해결 건).
- **완료일 칸 없음**: tasks에 완료일이 없어 마지막 진행 로그 날짜(없으면 등록일)로 근사한다. 2026-01~03 과제는 2026-05-20 일괄 등록이라 등록일이 실제와 다르다. 관찰·성운·재발 판정이 이 근사에 기대므로, 과제 완료일을 남기는 칸이 생기면 그 값을 쓴다.
- **날짜 근사**: 72건은 일자를 찾지 못해 `review_month` 15일이다(에어비앤비 70, 미매칭 2). 동대문 에어비앤비 1건은 raw 표기 「2026년 5월」이라 2026-05-15다.
- **LLM 1회 판정**: 별 추출, 현상 경계, 과제 연결은 사람 검수 전이다. FO 검수 항목은 validation.md 4절(욕실 바닥 젖음과 건습 분리 없음과 배수 막힘의 경계, 셀프 운영 번거로움 합침, 객실 냄새 범위, 「운영 밖」 별자리를 경보·수행과제 대상에서 어떻게 다룰지, 일괄 등록 과제 중 연결하지 않은 것).
- **CR 별 0**: 받는 쪽이 CR인 별이 없다. 관계 문제는 관계 신호(23개)로만 보인다.
- **주 기준 두 가지**: 별자리 판정은 ISO 주, 주간 리포트는 화~월 버킷이다. 같은 별이 두 기준에서 다른 주로 보일 수 있다.
- **새 표 인덱스**: advisors 성능 INFO 「Unused Index」 5건은 표를 만든 지 몇 분 뒤라 조회 기록이 없어서 나온 것이다. 앱이 쓸 인덱스라 두었다. 앱 가동 1~2주 뒤 다시 본다.
- **표 권한**: anon, authenticated에는 Supabase 기본 표 권한(INSERT, UPDATE, DELETE, TRUNCATE 등)이 남아 있다. API 쓰기는 RLS가 막는다. 권한을 회수할지는 정하지 않았다.
- **범위**: 신설·동대문, 2026-06~10만. 다른 지점은 같은 방식으로 나중에 붙인다.
