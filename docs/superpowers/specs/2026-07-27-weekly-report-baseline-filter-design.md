# 주간 리포트 — 기준선 미달 리뷰만 드릴다운 + 기준 점수 패널

- 날짜: 2026-07-27
- 선행 설계: `2026-07-24-weekly-report-quality-design.md` (논의 카드 중심 재편)

## 왜

FO Weekly 화면을 실제로 열어 보니 두 곳이 어긋나 있었다.

**1) 펼침이 판정과 다른 것을 보여 준다.** 동대문 Agoda 2026-07-20 카드는 `8.9 → 8.0 3건`이다.
「리뷰 보기」를 누르면 4.0 한 건과 10.0 두 건이 함께 뜬다. 카드가 말하는 것은 "누적 8.9를
끌어내린 주"인데, 펼침은 "그 주에 쓰인 리뷰 전부"를 준다. 10.0짜리 두 건은 점수를 끌어내리기는커녕
밀어올린 리뷰다. 회의에서 읽어야 할 것은 4.0 하나뿐인데 나머지 둘이 자리를 차지한다.

**2) 화면이 기준선을 밝히지 않는다.** 카드 오른쪽 작은 `8.9`가 기준선이지만, 그것이 그 채널
누적 점수라는 사실도, 다른 채널의 기준선이 4.00부터 9.30까지 흩어져 있다는 사실도 화면에
없다. 그래서 "왜 8.0이 미달인가"를 매번 말로 설명해야 한다. 페이지 오른쪽은 비어 있다.

## 무엇을 만드나

### A. 드릴다운을 기준선 미달 리뷰로 좁힌다

거르는 곳은 `lib/weeklyReviews.ts`의 `buildChannelReviews`다. 화면이 아니라 순수 함수 안이다 —
판정과 같은 층에 두어야 카드의 판정과 펼침의 목록이 기준선 **하나**를 공유한다. 화면에서 거르면
같은 기준을 두 벌 유지하게 되고, 한쪽만 고치는 순간 카드와 목록이 조용히 갈라진다.

**규칙: `rating < baseline`.** 판정(`judgeWeek`)과 같은 부등호다 — 경계값은 미달이 아니다.

환산은 하지 않는다. `raw_reviews.rating`은 채널 자기 척도로 저장돼 있다(야놀자 1~5,
에어비앤비 1~5, 나머지 1~10 — 2026-07-27 실측). `baseline`도 같은 채널의 값이므로 두 값의
척도가 항상 일치한다. `weeklyReport.ts` 상단이 같은 이유로 환산을 금지하고 있다.

**평점 없는 행은 남긴다.** 판정할 수 없는 것을 통과로 처리하지 않는다는 이 리포트의 원칙
(`verdict: 'unknown'`, `silent`)과 같은 이유다. 현재 실데이터에 null rating은 0건이지만
`numOrNull`이 이미 그 경우를 다루고 있으므로 규칙만 명시한다.

**`baseline == null`이면 거르지 않는다.** 드릴다운 대상은 `below` 채널뿐이라 실제로는 항상
값이 있지만, 기준선 없이 임의로 거르면 아무 근거 없이 리뷰가 사라진다.

`ChannelReviews`에 두 필드를 더한다.

| 필드 | 의미 |
|---|---|
| `hiddenCount` | 기준선 이상이라 목록에서 뺀 건수 |
| `baseline` | 화면이 "기준 8.9"를 출력하기 위한 값 (`null` 가능) |

`expectedCount`는 뜻을 바꾸지 않는다 — 판정이 쓴 그 버킷 총 리뷰 수 그대로다.

**커버리지 경고를 같이 고친다.** 지금 조건은 `items.length < expectedCount`다. 필터를 걸면
원문 3건을 다 확보했는데도 `items.length`가 1이 되어 "(원문 확보 1/3건)"이 뜬다. 분자를
**확보한 원문 총수 `items.length + hiddenCount`** 로 바꾼다.

**표시 문구 3종.**

```
리뷰 원문 · 기준 8.9 미달 1건            ← 확보 부족 시 뒤에 "(원문 확보 2/3건)"
[ 4.0 카드 ]
기준 8.9 이상 2건은 표시하지 않았습니다   ← hiddenCount > 0 일 때만
```

빈 상태는 두 가지를 **구분한다**.

| 상태 | 문구 |
|---|---|
| 확보한 원문 0건 | 원문을 찾지 못했습니다 — 수집 커버리지 밖의 리뷰입니다 (기존) |
| 확보했으나 전부 기준 이상 | 확보한 원문 N건이 모두 기준 8.9 이상입니다 — 점수를 끌어내린 리뷰는 수집 범위 밖입니다 |

합치면 안 된다. 아고다 raw 커버리지가 31~34%라 두 번째 상태는 실제로 나온다. 한 문구로 뭉치면
"수집이 안 됐다"와 "나쁜 리뷰만 수집에서 빠졌다"가 구분되지 않는다 — 후자는 수집 쪽 결함 신호다.

### B. 우측에 기준 점수 패널

`buildWeeklyReport`가 `baselines` 배열을 하나 더 낸다. **활성 채널 전부**(2026-07-27 기준 24개)를
담는다 — 그 주 리뷰가 0건인 채널도 뺀다. 기준 점수는 리뷰 유무와 무관한 채널의 속성이고,
빠지면 표에 구멍이 생겨 "이 채널은 왜 없지"를 회의에서 묻게 된다.

값은 카드와 **같은 `pickBaseline(snapshots, bucketEnd)`** 로 뽑는다. 채널마다 `bucketEnd`가
다르다(주 채널은 그 주 끝, 월 채널은 그 달 끝) — 각자 자기 버킷 끝을 쓴다. 이래야 좌우 숫자가
어긋나지 않는다.

```ts
interface BaselineRow {
  propertyId: number
  branch: string
  otaName: string
  scoreMax: number
  score: number | null
  recordedAt: string | null
  isFallback: boolean
  below: boolean       // 이번 버킷 판정이 'below'인 채널
}
```

**표시.** 지점 고정 순(신설 → 동대문 → 제주시티 → 고성), 지점 안은 OTA 고정 순. 미달 채널만
점수를 빨강 + 좌측 점을 찍어 왼쪽 논의 카드와 눈으로 이어지게 한다.

스냅샷 날짜는 전 채널이 같을 때만 헤더에 한 번 쓴다(`07-27 스냅샷`). 갈리면 "채널별 스냅샷"으로
바꾼다 — 대표값 하나를 찍으면 그 순간 화면이 거짓을 말한다.

**레이아웃.** 지금 `maxWidth: 900` 한 컬럼을 `900px + 280px` 2컬럼으로 넓힌다. 우측은
`position: sticky`로 스크롤을 따라온다. 폭이 좁아지면 1컬럼으로 접히고 패널이 카드 **아래**로
간다 — 위로 올리면 노션 임베드에서 논의 카드가 첫 화면 밖으로 밀린다. 이 저장소의 기존 방식대로
`app/globals.css`의 `@media` 블록에 클래스를 추가한다(인라인 스타일로는 미디어쿼리를 못 쓴다).

임베드 페이지(`app/embed/weekly-report`)는 같은 컴포넌트를 쓰므로 자동 적용된다.

## 테스트

**`weeklyReviews.test.ts`**
- 기준선 미만만 남고 이상은 `hiddenCount`로 센다
- 경계값(정확히 baseline)은 남지 않는다 — 판정과 같은 부등호
- 5점제 채널(야놀자 baseline 4.0)이 환산 없이 걸러진다
- 평점 null 행은 남는다
- `baseline == null`이면 전부 남고 `hiddenCount = 0`
- 필터가 걸려도 `expectedCount`는 판정이 준 값 그대로다

**`weeklyReport.test.ts`**
- `baselines`가 리뷰 0건(silent) 채널을 포함해 활성 전 채널을 담는다
- `below` 플래그가 `report.below`·미달 월 채널과 일치한다
- 월 채널이 자기 월 버킷 끝의 스냅샷을 쓴다(주 버킷 끝이 아니다)

## 추가 — 카드에서 '원인'을 제거한다 (같은 날, 재헌 결정)

위 A·B를 배포한 직후 실화면에서 잡힌 문제다.

**신설 Trip.com 2026-07-27**의 카드 결론이 `QR 코드 다크모드 인식 불편`인데, 그 주 미달
리뷰(6.0)는 "지하철·버스 가까워 편리, 욕조도 있어 편안"이라는 전혀 다른 내용이었다.

추적한 경로: 그 버킷의 `ota_complaints`는 `headline`·`memo`가 **둘 다 비어 있어**
`resolveHeadline`이 3단계 폴백(bad 키워드)까지 내려갔다. 거기서 집힌 키워드의 `band`는
**9점대** — 즉 그 주 다른 리뷰인 **9.5점**짜리의 팁이었다. 기준선 8.7을 **밀어올린** 리뷰의
사소한 지적이 **미달 주의 원인** 자리에 앉은 것이다.

이는 2026-07-24에 이미 한 번 잡은 실패 유형이다(그때는 "9점 리뷰의 `숙박비 부담`이 미달
원인처럼 읽힌다"는 이유로 bad 키워드를 결론 본문에서 뺐다). **폴백 경로만 밴드를 보지 않은 채
남아 있었다.** 밴드 필터를 덧대는 안도 검토했으나, 밴드가 `9점대`·`8~9점`·`6점대 이하` 등
자유 텍스트 15종이라 파서를 새로 얹어야 했고, 무엇보다 **리포트가 원인을 지어낼 이유가 없다**.

**결정: 주간 리포트 카드는 원인을 쓰지 않는다.** 카드가 말하는 것은 "기준 점수보다 낮은
리뷰가 났다"까지다. 왜 그랬는지는 펼침의 **리뷰 원문(번역본 포함)** 을 사람이 읽어 판단한다.

제거 범위:

| 대상 | 처리 |
|---|---|
| 카드의 결론 한 줄 / `⚠ 원인 미기록` | 삭제 |
| 펼침의 `상세`(memo 전문) · `키워드`(bad 키워드) | 삭제 |
| `WeeklyCause` · `HeadlineSource` · `HEADLINE_MAX` · `resolveHeadline` · `WeeklyChannelRow.cause` | 삭제 |
| `WeeklyReportInput.complaints` · `.voc`, `ComplaintRow` · `VocRow` | 삭제 |
| `pageData`의 `ota_complaints` · `ota_voc` 조회 | 삭제 (5분마다 두 표를 통째로 읽던 것이 사라진다) |
| `소표본 N건 · 추세 아님` 배지 (`isThinSample` · `THIN_SAMPLE_MAX` · `row.thinSample`) | 삭제 — 원인 한 줄이 사라진 뒤 카드에 남은 유일한 문구였고, 건수는 이미 헤더에 점수와 같은 크기로 찍혀 있어 중복이었다 |

배지까지 빠지자 버튼만 남은 둘째 줄은 여백일 뿐이라 **수치·버튼을 헤더 한 줄로 합쳤다**
(헤더 정렬 `baseline`→`center`, 카드 패딩 18→14px). 카드 하나가 한 줄이 되어 논의 5건이
스크롤 없이 한 화면에 들어온다.

펼침에 남는 것: 직전 주 대비·추정 방식·기준선 스냅샷(출처 표기)과 **리뷰 원문**뿐이다.
출처 표기는 리포트가 지어낸 문장이 아니라 값이 어디서 왔는지의 기록이므로 남긴다.

`ota_complaints.headline` 컬럼과 이를 쓰는 배치(`/parse-reviews` Part B)는 **건드리지 않았다** —
불만 분석 서브탭 등 다른 소비처가 있고, 이 결정은 주간 리포트가 그 값을 읽지 않는다는 뜻이다.

**부수 관찰(미해결).** 문제의 6.0 리뷰는 본문이 전부 긍정이다. 원문/번역본 이중 적재는
아니다(쌍둥이 행 없음을 확인). 트립닷컴 총점이 세부 항목 평균이라 텍스트와 점수가 어긋나는
것으로 보인다. 즉 이 주는 **텍스트상 원인이 실재하지 않는다** — 원인을 쓰지 않기로 한 결정이
이 케이스에서 정확히 옳게 동작한다.

## 하지 말 것

- 🔴 필터를 화면(클라이언트)에서 걸지 말 것. 판정과 목록이 기준선 하나를 공유해야 한다.
- 🔴 5점제 채널을 10점으로 환산하지 말 것. 두 값이 이미 같은 척도다.
- 🔴 `hiddenCount`를 조용히 버리지 말 것. 숨긴 사실이 화면에 남아야 "전부 본 것"으로 오독되지 않는다.
- 🔴 `baselines`에서 리뷰 0건 채널을 빼지 말 것.
- 🔴 **카드에 원인 한 줄을 되살리지 말 것.** 폴백으로 지어낸 원인은 기준선 위 리뷰의 지적을
  미달 원인으로 내보낸 전력이 있다. 원인은 리뷰 원문을 사람이 읽어 판단한다.
